# hx Threat Model

## Scope and method

This document establishes the architecture-level threat model for `hx` (a personal homelab and cloud observability system), defining assets, trust zones, trust boundaries, and threats using the STRIDE methodology.

**Implementation Status:** All runtime components, interfaces, and security controls described in this document are **Planned**. As of milestone F01 (issue [https://github.com/hndrxc/hx/issues/9](https://github.com/hndrxc/hx/issues/9)), no Go code, command binaries, or security controls have been implemented in the repository. This document records architectural commitments, boundaries, planned mitigations, and explicit residual risks before implementation.

The threat model evaluates thirteen primary trust boundaries (`TB1`–`TB13`) across eight trust zones (`Z1`–`Z8`). For each boundary, threats are categorized using the STRIDE classification:
- **S**poofing identity
- **T**ampering with data
- **R**epudiation
- **I**nformation disclosure
- **D**enial of service
- **E**levation of privilege

System context diagrams and component interaction sequences are defined in [Architecture Overview](../architecture/overview.md). Foundational architecture decisions are recorded in [ADRs](../adr/README.md).

## Assets

The threat model protects eight core asset categories:

- **A1: Provider credentials** — Scoped read-only API tokens, OAuth refresh tokens, and personal access tokens for third-party SaaS providers (Supabase, Vercel, GitHub, Cloudflare) and homelab management endpoints (iDRAC Redfish, VMware ESXi, TrueNAS SCALE, Home Assistant, Kopia). Integrations are read-only through Phase 3 and never authorize administrative credentials or database passwords. Held exclusively in the hub vault.
- **A2: Vault passphrase and unwrapped keys** — Operator master passphrase, Argon2id wrapping key, and XChaCha20-Poly1305 symmetric data encryption keys. The master passphrase is entered via local secure TTY prompt and conveyed over protected local admin IPC to the hub during unlock; held in hub process memory only while unlocked; never written to disk, audit log, or transmitted across remote RPC.
- **A3: Hub CA key and client enrollment credentials** — Hub private Certificate Authority (CA) private key (used to sign mTLS certificates for clients and agents), operator-approved single-use bootstrap enrollment tokens, and each client's and agent's own enrollment private key, certificate, and hub CA certificate. Clients and agents never hold other identities' private keys or provider secrets.
- **A4: tsnet node key and state** — Tailscale machine private keys, state files, and node identity maintained in the hub's local tsnet directory (`<hub state dir>/tsnet`).
- **A5: Monitoring state** — SQLite database containing topology records, collected metrics, historical observations, incident tracking states, and collector run metadata.
- **A6: Audit log** — Append-only, tamper-evident hash-chained event records capturing vault state changes, authentication outcomes, administrative commands, and collector executions.
- **A7: Alert delivery path** — Alert routing configurations, webhook endpoints (such as ntfy on the tailnet), deduplication state, and dispatch queues.
- **A8: Release artifacts and source code** — GitHub repository source code, CI/CD pipeline definitions, release binaries, software bill of materials (SBOM), and cryptographic signatures/provenance metadata.

## Trust zones

Trust boundaries separate eight discrete trust zones:

- **Z1: Operator workstation** — Operator environment running the `hx` CLI, Bubble Tea TUI, or `hx-desktop` (Wails v3 thin client). Holds operator client mTLS enrollment private key and certificate, and the hub CA trust root certificate. Never holds provider credentials, vault keys, or other node keys.
- **Z2: Devices** — Target hosts, servers, and laptops running `hx-agent`. Outbound-only; holds agent mTLS certificate and private key, and the hub CA trust root certificate. Never holds provider credentials, vault keys, or other device credentials.
- **Z3: Hub host** — Dedicated Debian 13 amd64 system running the `hx hub` daemon as an unprivileged service under systemd (`ProtectSystem=strict`). Houses the hub process, encrypted vault, SQLite database, tsnet state directory, and local admin Unix domain socket.
- **Z4: Tailscale SaaS** — Tailscale SaaS control plane (`controlplane.tailscale.com`, `login.tailscale.com`) and DERP relays. Trusted third party for node identity and reachability; transports WireGuard encrypted packets; provides node identity lookups via `LocalClient().WhoIs`. Reachability on the tailnet does not grant authorization.
- **Z5: Internet SaaS providers** — External SaaS APIs (Supabase, Vercel, GitHub, Cloudflare, public endpoints/DNS). Untrusted network endpoints queried over outbound HTTPS.
- **Z6: Homelab management network** — Local management controllers and appliances (iDRAC Redfish, VMware ESXi, TrueNAS SCALE, Home Assistant, Kopia). Local network endpoints queried over outbound HTTPS/TLS using private CA or pinned-leaf verification.
- **Z7: Notification endpoint** — ntfy notification server reachable over the tailnet. Receives outbound alert dispatch webhooks.
- **Z8: Local inference service** — Optional, isolated local inference runtime (Phase 3). Outbound read-only controller requests; no inbound access to hub state; advisory output only.

## Residual risks

The following mandatory architectural residual risks are recorded as explicit system boundaries and operational realities:

1. **In-process collector memory sharing (TB8):**
   `in-process collectors share memory/privileges`
   Built-in collectors are Go packages compiled directly into the hub binary and execute in the same operating system process. They share address space, file descriptors, and process privileges with the hub core. Manifest declarations, compiler package boundaries, and scoped context handles catch mistakes and constrain cooperative code, but they do not provide hardware-enforced or process-isolated security boundaries against adversarial code. Hard process isolation is deferred to the external-process plugin tier (milestone E01, [https://github.com/hndrxc/hx/issues/79](https://github.com/hndrxc/hx/issues/79)).

2. **Garbage collection and secret memory lifetime (TB7):**
   `Go cannot guarantee secret bytes are never copied by runtime/GC`
   The Go runtime and garbage collector do not provide memory-pinning or zero-on-free guarantees for heap-allocated buffers. Plaintext secret lifetimes are minimized using scoped handles and zeroing byte slices where possible, but copies created during string conversion or runtime stack growth cannot be reliably cleared.

3. **Audit log truncation detection (TB7):**
   `local hash chain detects edits but not truncation without off-host checkpoints`
   The hub audit log employs cryptographic hash chaining linking records sequentially. The hash chain guarantees consistency relative to a known trusted head or checkpoint. An attacker with host write access can rewrite or truncate the local log without detection unless off-host checkpoints exist; full local rewrite or tail deletion is not prevented solely from local disk state. Off-host checkpointing mechanisms are owned by milestone O03 ([https://github.com/hndrxc/hx/issues/51](https://github.com/hndrxc/hx/issues/51)) and S03 ([https://github.com/hndrxc/hx/issues/13](https://github.com/hndrxc/hx/issues/13)).

4. **Tailscale control plane trust boundary (TB6):**
   `Tailscale Inc. control plane is a trusted third party for node identity/reachability, mitigated but not eliminated by mTLS`
   The hub relies on the Tailscale SaaS control plane for WireGuard node key distribution, NAT traversal, DERP relaying, and `LocalClient().WhoIs` node metadata. While mTLS with the hub's private CA ensures that reachability on the tailnet does not grant authorization, a compromise or malicious action by Tailscale Inc. could route unauthorized traffic to the hub port or deny network connectivity.

5. **Reboot availability and vault lock state (TB7):**
   `hub vault is locked after every reboot, so secret-requiring collection stops until an operator unlocks`
   By design, the hub starts in an explicit `Locked` state following every process launch or host reboot. It requires an operator to provide the vault passphrase via a local interactive TTY (`hx hub unlock`). Until unlocked, secret-free operations, self-health checks, and telemetry queries continue, but all secret-requiring collectors cease polling and report `vault_locked`. Unattended unlock via vTPM or external KMS is out of scope for initial phases and deferred to milestone E03 ([https://github.com/hndrxc/hx/issues/81](https://github.com/hndrxc/hx/issues/81)).
