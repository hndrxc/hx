# Audit Log

**Status:** Implemented in `internal/hub/audit` by S03 ([#13](https://github.com/hndrxc/hx/issues/13)); the vault and TLS trust store use its decision hooks. Retention, deletion and production off-host replication are not implemented and belong to O03 ([#51](https://github.com/hndrxc/hx/issues/51)). The writer is Linux-only.

Threat context: A6 and T-TB7-R in the [threat model](threat-model.md).

## Event model

| Field | Type | Meaning |
|---|---|---|
| `At` | time | Event time, recorded in UTC |
| `ActorKind` | named string | `operator`, `client`, `integration`, `unknown` |
| `ActorID` | 16-byte ID | Nonzero stable actor ID |
| `IntegrationID` | 16-byte ID | Zero means not applicable |
| `Action` | named string | `vault_unseal`, `secret_access`, `api_auth`, `client_enrollment`, `client_connection`, the [vault lifecycle actions](#vault-lifecycle-events-s02), and the [TLS trust actions](#tls-trust-events-s05) |
| `Outcome` | named string | `allowed`, `denied`, `error` |
| `CorrelationID` | 16-byte ID | Nonzero; ties records of one attempt together |

Go names: `ActorOperator`, `ActorClient`, `ActorIntegration`, `ActorUnknown`; `ActionVaultUnseal`, `ActionSecretAccess`, `ActionAPIAuth`, `ActionClientEnrollment`, `ActionClientConnection`, `ActionTLSTrustApproval`, `ActionTLSTrustRotation`, `ActionTLSTrustReplacement`, `ActionTLSPinMismatch`; `OutcomeAllowed`, `OutcomeDenied`, `OutcomeError`.

### Identifiers

IDs are derived by callers from verified metadata (for example an authenticated certificate subject or enrolled record), never from raw request input, and never from secret material, passphrases, tokens, paths or payloads. For an unattributed denial or error, use `ActorUnknown` with a trusted opaque per-attempt ID generated by the hub; do not derive it from attacker-supplied data. Zero actor or correlation IDs are rejected.

## Wire contract (v1)

One record per line: compact JSON (no insignificant whitespace) terminated by a single LF (`\n`). A frame, including its LF, is at most 1024 bytes. Keys appear in this exact order, produced by the Go compact struct encoding:

`version`, `sequence`, `previous`, `time`, `actor_kind`, `actor_id`, `integration_id`, `action`, `outcome`, `correlation_id`, `hash`

- `version`: `1`.
- `sequence`: first record is 1; each record is the previous plus 1.
- `previous`: hash of the preceding record; genesis is 64 `0` digits.
- `time`: UTC, `time.RFC3339Nano`.
- Enums: lowercase ASCII snake_case values (`vault_unseal`, `allowed`, ...).
- IDs (`actor_id`, `integration_id`, `correlation_id`): exactly 32 lowercase hex digits, no dashes. A zero `integration_id` is 32 zeros.
- `hash`: lowercase 64-digit hex SHA-256 over the same compact JSON struct **without** the `hash` key (and without the LF). The frame is the whole struct including `hash`, then LF.

### Checkpoint

`Checkpoint{Sequence uint64 "sequence"; Hash string "hash"}`. `Genesis()` returns sequence 0 and 64 zeros. A checkpoint file is the JSON form of this struct.

## Verification

`Verify(r io.Reader, anchor *Checkpoint) (Checkpoint, error)` verifies from genesis through the final record and returns the head. If an anchor is given, the chain must contain exactly that sequence and hash as a matching prefix; the anchor may be below the final head. Errors never echo untrusted record content; they may include the expected sequence.

### CLI

```
hx audit verify LOG [--checkpoint FILE]
```

`LOG` is the audit file. `--checkpoint FILE` supplies a trusted checkpoint JSON file as the anchor. Without it only internal consistency from genesis is proven.

## Writer and call ordering

`Open(path, OpenOptions{Anchor *Checkpoint, RecoverTail bool})`, `Log.Append(Event) (Checkpoint, error)`, `Log.Close()`. Append encodes the frame, writes and syncs it, and returns the new head only on success.

### Typed hooks

Hooks are typed, not free-form. `Hooks` is built with `NewHooks(log)`; a nil `*Hooks` or zero value fails closed with `ErrHooksUnconfigured`. Methods take verified metadata and an outcome and return `error`:

```go
type Meta struct { At time.Time; ActorKind ActorKind; ActorID, IntegrationID, CorrelationID ID }

func (h *Hooks) VaultUnseal(m Meta, o Outcome) error
func (h *Hooks) VaultLifecycle(a Action, m Meta, o Outcome) error
func (h *Hooks) SecretAccess(m Meta, o Outcome) error
func (h *Hooks) APIAuth(m Meta, o Outcome) error
func (h *Hooks) ClientEnrollment(m Meta, o Outcome) error
func (h *Hooks) ClientConnection(m Meta, o Outcome) error
func (h *Hooks) TLSTrustApproval(m Meta, o Outcome) error
func (h *Hooks) TLSTrustRotation(m Meta, o Outcome) error
func (h *Hooks) TLSTrustReplacement(m Meta, o Outcome) error
func (h *Hooks) TLSPinMismatch(m Meta, o Outcome) error
```

- `SecretAccess`, `vault_secret_put`, and `vault_secret_delete` require a nonzero `IntegrationID`.
- An `ActorUnknown` actor must not be recorded as `allowed`.
- **Privileged successes** (unseal, secret access, enrollment, an allowed authentication or connection) are recorded **before** the grant takes effect. Grant only when the hook returns nil; if it fails, the operation fails closed.
- **Denials and errors** stay denied if the audit write fails; an audit failure never turns a deny into an allow.
- Audit write failures surface to telemetry as sanitized, fixed-category signals only: no event contents, IDs from untrusted input, paths or error text containing record data.

### Vault lifecycle events (S02)

`VaultLifecycle` accepts `vault_initialize`, `vault_rotate`, `vault_lock`, `vault_backup`, `vault_restore`, `vault_secret_put`, and `vault_secret_delete`. See [vault.md](vault.md) for ordering, including key erasure on lock even when its audit write fails. Frames retain the v1 shape and hash rules. A pre-S02 verifier will reject logs that contain these new actions; use an updated verifier.

### TLS trust events (S05)

S05 ([#16](https://github.com/hndrxc/hx/issues/16)) adds four typed actions for the TLS trust store: approval, rotation (staging a successor), replacement (promoting the staged record) and pin mismatch. See [tls-trust.md](tls-trust.md) for the store semantics.

- **Audit-first authorization.** The trust store records an approval, rotation or replacement before it publishes the change. It proceeds only when the hook returns nil. An `allowed` outcome proves authorization was recorded, not that the filesystem publication succeeded: a recorded approval may never take effect (for example the store write fails afterwards). Treat the store state, not the audit record, as the source of truth for what is trusted.
- A pin mismatch is a denial; an audit failure never turns it into an allow.
- **Wire compatibility.** The frame shape, key order, version and hash rules are unchanged; only new `action` values appear. A verifier built before S05 validates `action` strictly and rejects the new values, so a log containing TLS trust events fails verification there. Keep an updated verifier for any log that contains TLS events, and do not verify such logs with an older binary.

### Durability and sync protocol

- The log lives in a trusted, private, local directory. The file must be a regular file owned by the current user with mode `0600`; it is opened with `O_NOFOLLOW`.
- `Open` takes an exclusive non-blocking `flock` held for the life of the `Log`; a mutex serializes `Append` within the process.
- On open the parent directory is synced, the whole chain is verified, and the file is synced.
- Each `Append` issues a single `O_APPEND` write of the whole frame and `fsync`s before returning success. The head advances only after both succeed.
- A short write, or any uncertain write or sync failure, poisons the log: every later `Append` returns `ErrLogPoisoned`. The persisted state is then unknown, and an uncertain frame may appear after the log is reopened. Reopen and re-verify.
- There is no multi-file atomicity: the audit record and the privileged work it guards are not committed together. Record first, then grant; a recorded grant may never take effect.

A crash can leave a torn, non-LF-terminated tail. The verifier reports it as `ErrTornTail` only when it is a bounded suffix after every complete record validated and any anchor matched. Oversized lines, a missing anchor, or any other malformed content are never reported as a torn tail.

## Crash procedure

There is no recovery CLI: `hx audit verify` is verify-only. Operator integration of tail recovery is through the Linux `OpenOptions{Anchor, RecoverTail: true}` API.

1. Stop the hub. Preserve an untouched copy of the original file first.
2. Obtain a trusted anchor (latest off-host checkpoint). Use `Genesis()` only when it is historically appropriate, for example the log was in fact created fresh.
3. Run `hx audit verify LOG --checkpoint FILE` on the preserved copy to confirm the diagnosis.
4. Recovery is opt-in and needs the copy and the trusted anchor: `Open` with `RecoverTail: true` and an explicit anchor. It trims only the bounded torn tail and preserves all complete frames. Without an explicit anchor, recovery is refused.
5. Retain the preserved original with the incident record.

## Safety limits

- A clean removal of records beyond the trusted anchor, or a removed suffix that was rehashed into a valid chain, is accepted. Detection requires a trusted anchor at or past the point of tampering.
- Root (or anyone who can write the file and the checkpoints) can forge an entire chain.
- Timestamps are not checked for wall-clock monotonicity; clocks can be wrong or adjusted.
- The chain proves ordering and integrity relative to an anchor, not authorship.

## Export

Export is a full-file, stable JSONL copy of the active chain to an external store. Take it only while writes are quiesced (hub stopped or the log closed). Verify the copy and compare the newly exported checkpoint with the last published one before publishing off-host: the new head must extend the old one. Publish the head checkpoint alongside the copy. The active chain keeps growing.

An anchor can cover an existing prefix even if the log is untrusted after it: the verifier proves that the prefix up to the anchor matches, and nothing about records beyond it.

## Rotation policy

Rename, truncate and copytruncate rotation of the active chain are unsupported: they break sequence and anchor continuity and can look like tampering or truncation. Instead export quiesced copies to an external store and keep the active growing chain.

## Retention, capacity and rollback

Capacity alerting is an operator action; the writer does not implement it. Deleting or expiring records, long-term retention and production replication are not implemented (O03, [#51](https://github.com/hndrxc/hx/issues/51)). Rolling back to an older copy of the file or an older checkpoint is a truncation: it verifies unless a newer trusted anchor is supplied, so keep the latest checkpoint off-host and never roll an anchor backward.
